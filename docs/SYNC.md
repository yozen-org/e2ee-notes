# 同期とペアリングのデータフロー

端末間でノートを同期する仕組みを、クライアントとサーバーのデータのやり取りに
絞ってまとめます。サーバーの HTTP API の詳細は
[`spec/EXCHANGE_SERVER_V1.md`](../spec/EXCHANGE_SERVER_V1.md)、暗号形式は
[`spec/KEY_ENVELOPE_V1.md`](../spec/KEY_ENVELOPE_V1.md) と
[`spec/OPERATION_V1.md`](../spec/OPERATION_V1.md) を参照してください。

## 鍵の階層

データは 3 段階の鍵で守られています。

```text
ハードウェア（Secure Enclave / Keystore / TPM）
   └─ 保護する: vault 鍵（32バイト・ルート鍵）
               └─ ラップする: room 鍵（32バイト）
                              └─ 暗号化する: 操作（ノートの編集ログ）
```

- **vault 鍵**: 端末のハードウェアで保護され、サーバーには出ません。端末間では
  QR で直接やり取りします。
- **room 鍵**: ランダム生成され、vault 鍵で AES-256-GCM にラップして
  `room.json` に保存します（`RoomRecord`）。
- **操作**: ノートの作成・編集・削除を表す追記型のログで、room 鍵で暗号化します。

## ストレージに置かれるオブジェクト

`BlobStore`（ローカルはファイルシステム、リモートはサーバー）には次の 2 種類の
オブジェクトが入ります。どちらも暗号文（または暗号文＋平文の識別子）です。

```text
room.json                                             … room 鍵を vault 鍵でラップしたもの
rooms/<roomId>/operations/<operationId>.json           … 操作（room 鍵で暗号化）
```

操作は追記型で、各オブジェクトは不変です（同じキーには同じ内容）。
削除も「delete 操作を追記する」トゥームストーン方式で、物理削除はしません。

## namespace の導出

サーバーは複数利用者のデータを区別する必要がありますが、中身を読めません。
そこでクライアントが vault 鍵から namespace を一方向に導出し、オブジェクトキーの
接頭辞に使います。

```text
namespace = SHA256( "yozen.e2ee-notes.sync-namespace.v1" || vault鍵 ) を hex 表記
```

- 同じ vault 鍵を持つ端末は同じ namespace を導出します（＝同じデータにアクセス）。
- 一方向のため、namespace から vault 鍵は復元できません。
- サーバーが見るのは namespace と暗号文だけです。

## サーバー（交換サーバー）

永続のゼロ知識 BlobStore です。`e2eenotes.yozen.org` にデプロイしています。

| メソッド | パス | 役割 |
|---|---|---|
| `PUT` | `/v1/objects/{key}` | オブジェクト保存（不変・上書きしない） |
| `GET` | `/v1/objects/{key}` | 取得 |
| `GET` | `/v1/objects?prefix={prefix}` | キー一覧 |
| `DELETE` | `/v1/objects/{key}` | 削除（将来のトゥームストーン回収用） |

サーバーが保持するのは `key`（namespace 込み）と `value`（暗号文）だけです。
TTL も一回きり削除もありません。参照実装は Hono で、ストレージを差し替えることで
Cloudflare Workers（KV）とセルフホスト（Node.js・インメモリ）の両方で動きます。
仕様は言語非依存なので、Go など任意の実装と相互運用できます。

## 同期の流れ

クライアントはローカルとリモートの `BlobStore` を「追記型のマージ」で揃えます。

```text
同期（syncBlobStores）
  1. リモートにだけあるオブジェクトをローカルへコピー（pull）
  2. ローカルにだけあるオブジェクトをリモートへコピー（push）
  3. NotesService がローカルの操作ログを読み、LWW で射影してノートを表示
```

操作が不変・追記型なので、競合解決は不要です（複雑な CRDT は使いません）。
同期のトリガーは次の 3 箇所です。

- **起動時**（Bootstrap が vault を開いた直後）
- **編集直後**（ノートの保存・削除の直後）
- **前面復帰時**（アプリが `resumed` になった時）

同期はベストエフォートで、サーバーに到達できなくてもローカルのノートは使えます。
サーバー URL はユーザーが変更でき（ペアリング画面 → 交換サーバー設定）、
自己ホスト先を指定できます。

## ペアリングの流れ

新しい端末に vault 鍵を渡す処理です。鍵はサーバーを経由せず、QR で直接交換します。

```text
受信側（新しい端末）                     送信側（既存の端末）
  1. createRecipientKey → 公開鍵 QR
      （表示して送信側に読み取らせる）
                                          2. 公開鍵 QR をスキャン
                                             envelope(vault鍵, 公開鍵) → エンベロープ QR
      （エンベロープ QR をスキャン）
  3. accept(エンベロープ) → vault 鍵を取得
  4. importVault … vault 鍵を自端末のハードウェアで再保護して保存
  5. 同期 … サーバーから操作ログを pull
```

ペアリング後は、受信側も同じ vault 鍵（＝同じ namespace）を持つため、
サーバーからデータを取得して復号できます。

## セキュリティモデル

- **ゼロ知識**: サーバーが保持するのは暗号文と namespace のみ。ノートの内容・鍵は
  復号できません。
- **鍵はサーバーを経由しない**: vault 鍵の交換は QR で端末間直接。サーバーには
  ラップ済みのエンベロープすら送りません。
- **能力モデル**: namespace を知る者のみが一覧・取得できます。namespace は
  256 ビットの乱数（vault 鍵の SHA-256）なので推測困難です。
